# openAut manuals archive contract

The `openaut/manuals` repository is a product library. Site names, building names, equipment tags,
and project-specific generated documents do not belong in its product paths.

## Repository layout

```text
catalog.yaml
manufacturers/
  siemens/
    desigo-pxc4/
      pxc4-e16/
        product.yaml
        documents/
          engineering-manual/
            en/
              a6v12345678/
                rev-2025-04/
                  manual.md
                  source.pdf
```

IDs and paths use lowercase ASCII slugs. Display names preserve the manufacturer's spelling.
The archive must contain no symbolic links. Each revision directory contains exactly `manual.md`
and one `source.<extension>` file; validation rejects misplaced contract files and any extra entry.
Ingest stages a complete new product or revision in a temporary sibling of the archive before
publishing it with an atomic no-replace rename. Linux and Windows are supported, and the helper
verifies that staging and destination use the same filesystem. Failed ingest attempts must not
expose a partial product or revision inside the archive or block a retry.
On POSIX, the helper aligns the published root's group and mode with its destination parent before
publication. On Windows, the archive and its parent must use the same ACL because a same-volume move
retains the staging directory's security descriptor rather than inheriting a new one.

## Product identity

`product_id` is `<manufacturer-id>.<family-id>.<model-id>`, for example
`siemens.desigo-pxc4.pxc4-e16`. It identifies a product model, not a physical installation.

`product.yaml` has this shape:

```yaml
schema: openaut-product/v1
product_id: siemens.desigo-pxc4.pxc4-e16
manufacturer: Siemens
manufacturer_id: siemens
product_family: Desigo PXC4
product_family_id: desigo-pxc4
model: PXC4.E16
model_id: pxc4-e16
aliases: []
tags: []
```

Do not rename an established ID merely because display spelling changes. Create aliases or a
reviewed migration when two records are discovered to represent the same product.

## Document identity and frontmatter

A document revision is unique by product, type, document number, language, and revision. Every
`manual.md` starts with YAML frontmatter:

```yaml
---
schema: openaut-manual/v1
document_id: siemens.desigo-pxc4.pxc4-e16.engineering-manual.a6v12345678.en.2025-04
title: Siemens PXC4.E16 engineering-manual
product_id: siemens.desigo-pxc4.pxc4-e16
manufacturer: Siemens
product_family: Desigo PXC4
model: PXC4.E16
document_type: engineering-manual
document_number: A6V12345678
revision: 2025-04
language: en
protocols:
  - bacnet
tags: []
source:
  original_filename: A6V12345678.pdf
  stored_filename: source.pdf
  media_type: application/pdf
  sha256: 64-lowercase-hex-characters
conversion:
  method: ai-assisted
  converted_at: 2026-09-01
trust_level: quarantine
---
```

Allowed document types are:

- `installation-manual`
- `engineering-manual`
- `operation-manual`
- `programming-manual`
- `service-manual`
- `datasheet`
- `protocol-reference`
- `wiring-diagram`
- `certificate`
- `other`

Allowed trust levels are `untrusted`, `quarantine`, `verified`, and `superseded`. Only a reviewed
change may set `verified`. When superseding a revision, keep the old revision for audit and set its
trust level to `superseded`; do not delete it.

Use a BCP 47 language tag such as `en`, `sv`, or `en-GB`. `protocols` and `tags` are normalized
lowercase search terms. Document-specific scope notes and conversion uncertainty belong in the
Markdown body.

## Catalog

`catalog.yaml` is generated by `manual_archive.py catalog`. It is a portable index for consumers
that cannot query Systemdatabasen. Do not hand-edit it. Each entry includes the product identity,
document metadata, relative Markdown and source paths, source hash, Markdown hash, trust level, and
an unpinned `forge://openaut/manuals/...` URI.

At retrieval time, pin the URI to a reviewed commit and independently compare the fetched Markdown
blob with the hash registered in `system.documents.sha256`.

## Systemdatabas relationship

Use these logical relationships even if the deployment's physical schema evolves:

```text
system.equipment.product_id -> system.products.product_id
system.documents.product_id -> system.products.product_id
```

A product document normally has no site or equipment ownership. Site-specific DU documents,
wiring as-built records, and generated integration artifacts stay in their appropriate Forge repos
and may link directly to `equipment_id`.
